    Chapter 3 — Your first project #

    A real project: a Wordle variant, live on GitHub Pages, built with a model collaborator — and your first decisions on the record. Budget ~60 minutes; each step shows its own estimate, and your actual times are something we genuinely want to hear about. One path; each step says how to verify it worked.

    A GitHub account ~4 min

    ☰
    GitHub is where your project’s code, its decision records, and (in a few steps) its live website all live. If you already have an account, enter your username below and skip to P2.

    Go to github.com/signup. Don’t stall on the username — you can change it later (Settings → Account), add or swap email addresses, all of it. Pick something and move.

    Then tell the guide who you are — this stays in your browser and personalizes every command below:

    Recruit your collaborator — mission and project, one paste ~12 min

    ☰

    Builds on: Clone it, open it, Claude Code

    This is the step that makes the project different from a chat window. You’re not summoning a tool — you’re recruiting a collaborator into a mission, and the difference is enacted, not poetic: they read the mission first, consent to it, and pick their own name. The paste below carries the mission AND the project, so one message starts everything.

    In the VS Code terminal, run claude. First launch in a new folder asks setup questions — trust the folder (yes — it’s your own repository), and project MCP servers (skip/decline for now: the template’s server wants Node, which this path doesn’t install; nothing in this hour needs it).

    Then paste this — the mission and the project together, one message (edit the project half freely; it’s yours):

    Hello — I have a mission for you: my first deliberatively-built project. Read CLAUDE.md and tell me if you accept — any pushback welcome. If you accept: configure the template (the ⟦⟧ placeholders and whatever else it asks), introduce yourself, and then we start on this:

The project is a Wordle variant — guess the word, colored feedback per letter — with a twist: the answers are computer science words (ARRAY, STACK, QUEUE, CACHE, TOKEN…). I want it hosted free on GitHub Pages, built with Vue using scoped CSS so styles stay component-local. Before you write any code: what are the 2–3 decisions we should settle first? Put them to me as proper QST cards in the record — with your recommendation on each.

    They’ll read, decide, name themselves, fill the template’s placeholders (asking you for anything that’s genuinely yours to answer), commit the configuration — and then turn to the project.

    ✓ You know it worked when: your collaborator has a name; CLAUDE.md’s AI line carries it; git log shows their configuration commit

    The questions come back ~5 min

    ☰

    Builds on: Recruit your collaborator — mission and project, one paste

    A good first ask carries the what and leaves the how open — which is why your paste asked for decisions, not code. What returns is the methodology’s native move, and it’s worth reading slowly the first time.

    What comes back will look something like this (a real emission from this exact blurb — yours will differ, and should):

    QST-VUE-SHAPE: single-file Vue from a CDN, or a Vite build with an Actions deploy? #

    • Status: unanswered
    • Why asking: “Vue with scoped CSS on GitHub Pages” hides a real fork — scoped CSS is a single-file-component feature, and SFCs want a build step.

    Options:

    • A — One index.html, Vue from a CDN: no build, push and it’s live. But “scoped” CSS becomes a naming convention we keep by discipline.
    • B — Vite project + GitHub Action deploying to Pages: true scoped styles, the standard modern path. Costs one workflow file.

    Recommendation: B. Rationale: the project’s own stated constraint is scoped CSS — A quietly downgrades it from a language feature to a promise. Confidence: 0.7. If wrong: if deployment fights us past ~15 minutes, I pause and ask you whether to relax scoped CSS, extend the budget, or pick another path — and we record whichever trade-off you accept.

    Notice the If wrong doesn’t quietly give away the thing the recommendation was protecting — it hands the trade-off back to the decider. If a falsifier ever relaxes your own requirement without asking you, send it back.

    Notice what that is: options you can weigh without leaving the block, a committed position, and the fact that would change it. Two or three like it are now in your docs/adr/ folder, waiting for you.

    ✓ You know it worked when: your collaborator answered with QST cards, not code — each carrying options, a recommendation, and an If wrong: line

    Your first answers ~12 min

    ☰

    Builds on: The questions come back, VS Code extensions

    Each card has a recommendation: their pick, the reasoning, a confidence, and (read this part twice) an If wrong: line naming what would change their mind. That last line is the heart of the method: a position stated so it can be checked, not performed so it can be believed. You are the decider; the cards protect your attention — because the reasoning is on the page, agreeing costs you two words.

    Pick one place to answer — both read and write the same files, and seeing that is the lesson:

    1. The extension: click the ADRs-for-AI icon in VS Code’s sidebar — open questions appear as a list; open one, read the recommendation, type your answer in the ANS box. (“A, agreed.” is a complete answer when you agree — the why is already on the page. Diverging? Then say why; the slot has no size limit.)
    2. The file itself: open the ADR, find each card’s **ANS:** line (the [Fill this in] placeholder marks the blank), type your answer, save. There is no database — and now you know it.

    Then notify: in the terminal, tell your collaborator “I’ve answered everything — read and proceed.” They read your answers from the files, update the records, and start building — no re-explaining. The record carried it.

    ✓ You know it worked when: every QST shows answered (the extension’s list drains to zero), and your collaborator is building

    Tweaks, the deliberate way ~8 min

    ☰

    Builds on: Ship it

    The first change after a build is where vibe coding usually starts shedding context. Not here — one more decision, on the record.
    Pick any tweak you actually want — hard mode, a streak counter, dark theme, more words, a hint system. Ask for it the same way: “I want X — if there’s a real fork in how, QST it; if not, just build.” Small tweaks won’t need a card; one of yours probably will. Answer it whichever of the four ways you liked best.

    ✓ You know it worked when: the tweak is live, and grep -rn '^### QST' docs/adr/ shows your decisions accumulating — that grep is retrieval enough for this first walk

    The capstone: can a stranger recover the why? ~8 min

    ☰

    Builds on: Tweaks, the deliberate way

    Chapter 1 promised that the why survives the conversation that produced it. That’s a testable claim, and you’re about to test it — on a session with no memory of anything you did today.

    Your collaborator knows why everything is the way it is — but they were there. The records only matter if someone who wasn’t can recover the reasoning. Test it:

    Open a new terminal in the project and start a fresh session (claude — a new session has no memory of today). Paste:

    Read the project records in docs/adr/. Identify one decision we made, an alternative we rejected, why we rejected it, and what would make us reconsider. Point to the file and section for each. If something is missing from the records, say so rather than reconstructing it.

    Compare the answer with what actually happened. Success is supported reasoning and honest gaps — not a plausible story. Then try the second half: name one changed constraint (say, “word packs per course week are now wanted”) and ask whether any recorded decision should reopen. Watch the If wrong lines earn their keep.

    That — not trust, not vibes — is what the records were for.

    ✓ You know it worked when: the fresh session points to the file and section for a decision, a rejected alternative, the why, and the reopen condition — or honestly names what’s missing instead of inventing it

    The crew, one click (optional extension) ~4 min

    ☰

    Builds on: Recruit your collaborator — mission and project, one paste

    Real projects grow more than one collaborator session, and reopening them one by one gets old. The template ships the cure — but its full machinery (tmux, the pneumatic launcher) is beyond this guide’s installed path, so this is an extension to do with your collaborator, not a required step.

    In the project terminal:

    just refresh-terminals

    …then ⌘-shift-P → Terminals: Run. Every configured session launches at once. Tomorrow: code ., one Terminals: Run, and the crew is back — reading the records you both wrote today, remembering why everything is the way it is.

    ✓ You know it worked when: Terminals: Run opens your collaborator’s terminal(s) automatically
